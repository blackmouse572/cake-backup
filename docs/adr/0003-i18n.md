# Translations: i18next with one typed string catalog shared by the app, the website and the server

Cage is Vietnamese first, English second, and should be able to add languages for other countries. The app, the circle's website and the server (SMS and Zalo messages, later) all show the same words, and the glossary terms must not drift between them. So every user-facing string lives in `packages/i18n`, keyed by a dot path such as `checkIn.imSafe`.

## How it works

- **One JSON file per language** in `packages/i18n/languages/`. Vietnamese is the source: `vi.json` defines the keys, a language missing a key fails the type check, and a test fails on extra keys. A string missing at runtime falls back to Vietnamese.
- **Locales** are `vi` (default) and `en`: BCP 47, lowercase, no region. Each language is named in itself everywhere ("Tiếng Việt", "English").
- **i18next** does the translating (`t`, `{{name}}` interpolation, fallback to Vietnamese), with **react-i18next** (`useTranslation`) in the app and on the website. The catalog is typed through i18next's `CustomTypeOptions`, so a typo in a key fails the build.
- The app has one instance and switches with `changeLanguage`. The website renders on the server, where each request may want another language, so it uses one fixed instance per locale (`i18nFor`).
- **Formats** follow the design system: 21:38 (24-hour, Vietnam time unless told otherwise), 3/11/2026, 2,4 km, 180 m.
- **Copy rules are tested:** no exclamation marks in any locale, and the check-in call strings never contain "Cage", "an toàn", "cảnh báo" or "công an".

## Which language is shown

- **App:** on first launch, the phone's language if it is Vietnamese or English, otherwise Vietnamese. The user's choice is saved on the device and applies at once.
- **Circle website:** the traveller's language (sent when the journey starts), unless the viewer picks another with `?lang=`, which is remembered in a cookie.
- **Check-in call, SMS and Zalo messages:** always the traveller's language.

## Considered options

- **A small hand-written `t` function.** It was the first draft. Jaden asked for a library instead of reinventing one. i18next brings plurals, context, namespaces and lazy loading when we need them, and it works the same in React Native, server rendering and a Worker.
- **Lingui or FormatJS.** Both are good, but they lean on build-time extraction or ICU syntax, which adds a compile step to every workspace for two languages. i18next is the most common choice with React Native.
- **Separate catalogs per app.** The glossary terms would drift, and the server and the website need the same alert wording.

## Consequences

- Adding a language means adding a JSON file and a locale code; the type check lists every missing string.
- Strings are bundled into each app. That's fine at this size; split by screen if the catalog grows large.
